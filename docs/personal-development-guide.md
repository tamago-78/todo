# 個人開発のやり方ガイド

このリポジトリ（Todoアプリ）を題材に、個人開発をどう進めればいいかをまとめたガイドです。
すでにこのリポジトリには React + TypeScript + Vite + テスト + Linter という個人開発に十分な土台が揃っているので、これを活かす前提で書いています。

## 全体の流れ

個人開発は大きくこの5ステップの繰り返しです。

1. **作るものを決める**（小さく）
2. **動く最小版（MVP）を作る**
3. **自分で使ってみる**
4. **公開する**
5. **フィードバックをもとに改善する**

一番よくある失敗は「1で大きくしすぎて2が終わらない」ことです。最初の目標は「1〜2週間で自分が毎日使えるもの」に絞りましょう。

## 1. 作るものを決める

- **自分が欲しいものを作る**のが鉄則です。ユーザー第1号が自分なら、モチベーションも続き、フィードバックも即座に得られます。
- アイデアは「不便に感じた瞬間」をメモしておくと貯まります。
- 決めたら、機能を「必須 / あとで / やらない」の3つに分類し、必須だけで最初のバージョンを定義します。

例：このTodoアプリなら「タスクの追加・完了・削除ができる」が必須で、QRコード共有やPWA化は「あとで」に入る機能です。

## 2. 開発環境と日々の進め方

### このリポジトリでの基本コマンド

```bash
npm install        # 初回のみ：依存パッケージのインストール
npm run dev        # 開発サーバー起動（ブラウザで即確認できる）
npm test           # テスト実行（vitest）
npm run build      # 本番用ビルド
```

### Gitの使い方（1人でもブランチを切る）

1人開発でも `master` に直接コミットせず、変更ごとにブランチを切るのがおすすめです。

```bash
git switch -c feature/add-due-date   # 作業ブランチを作る
# ...開発...
git add -A && git commit -m "期限日を追加できるようにする"
git push -u origin feature/add-due-date
```

- コミットは「1つの変更 = 1コミット」を意識し、メッセージは日本語でOK。「何をしたか」より「なぜしたか」が伝わると後で助かります。
- GitHub上でPull Requestを作ってからマージすると、変更履歴が読みやすくなります（このリポジトリのPR #1 がまさにその例です）。

### AI（Claude Codeなど）との分担

- **AIに任せると速いこと**：ボイラープレート作成、テスト追加、リファクタ、エラーの原因調査、ライブラリの使い方調査。
- **自分でやるべきこと**：何を作るかの判断、実際に触っての使い心地チェック、公開してよい内容かの最終確認。
- AIが書いたコードも `npm test` と `npm run dev` での動作確認は必ず自分で行いましょう。

## 3. 品質を保つ最低限のライン

このリポジトリにはすでに揃っていますが、個人開発で持っておきたいのはこの3点です。

| 仕組み | このリポジトリでの実体 | 役割 |
|---|---|---|
| Linter | ESLint（`.eslistrc.json`） | バグの芽を機械的に検出 |
| Formatter | Prettier（`.prettierrc.json`） | 整形を自動化して迷いをなくす |
| テスト | Vitest（`src/__tests__/`） | 壊したことにすぐ気づける |

テストは全部に書く必要はありません。`src/lib/isTodos.ts` のような**ロジックが集中している関数**にだけ書けば十分効果があります。

## 4. 公開する

Webアプリの公開先は無料枠で十分です。

- **GitHub Pages**：このリポジトリはすでに `gh-pages` パッケージと `static.yml` ワークフローがあるので、一番手軽です。
- **Vercel / Netlify / Cloudflare Pages**：GitHubリポジトリを連携するだけで、pushのたびに自動デプロイされます。独自ドメインやプレビューURLが欲しくなったらこちら。

### 公開前チェックリスト

- [ ] APIキー・パスワード等の秘密情報がコードやコミット履歴に含まれていない（`.gitignore` の確認、`.env` はコミットしない）
- [ ] 個人情報や社内情報が含まれていない
- [ ] READMEに「何のアプリか・どう使うか」を書いた
- [ ] スマホでも表示を確認した

**注意**：公開は取り消しにくい操作です。リポジトリ自体をpublicにする場合は、履歴全体に見られて困るものがないか公開前に必ず確認しましょう。

## 5. 続けるコツ

- **小さく完成させる**：未完成の大作より、動く小品。リリースすること自体が最大の学びです。
- **毎回「次にやること」をIssueに残して終える**：再開時のハードルが下がります。GitHubのIssueがそのままTODOリストになります。
- **飽きたら捨てていい**：個人開発は学びが目的でも十分。リポジトリが残っていればポートフォリオになります。

## 次のステップの例（このTodoアプリの場合）

- タスクに期限や優先度を追加する
- ドラッグ＆ドロップで並び替え
- ダークモード対応
- GitHub Pagesで公開して友人に使ってもらう

まずは1つ選んでブランチを切り、小さく作って動かすところから始めましょう。
